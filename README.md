# Chore Tracker

Chore Tracker is a self-hosted chore tracker for one household. A child picks
their profile from a shared device, sees the chore assigned to them for the
current Monday-Sunday week, and checks off each checklist item as it is done.
An administrator manages the family and chore catalog, reviews immutable weekly
reports, and signs in with a passkey.

The app is deliberately small: a FastAPI and SQLite backend, a React and Vite
frontend, and deployment assets for Docker Compose and a single-replica
homelab Kubernetes cluster.

## MVP scope

### Included

- Household profile selection without child accounts, passwords, or child
  authentication.
- Deterministic Monday-Sunday chore rotation. Every active child receives one
  chore for the week when there are at least as many active chores as active
  children.
- Required and optional checklist items, with daily per-item completion,
  unchecking, and a durable per-day history.
- Immutable weekly completion reports generated by the Monday rollover,
  viewable only by signed-in administrators, with a durable per-child
  reward-given audit record.
- Manual weekly assignment generation for a selected week by an administrator,
  using the same deterministic rotation as the scheduled rollover.
- One-day claims for chores the weekly rotation left unassigned, without
  administrator approval and without changing the weekly schedule.
- Passkey-based administrator sign-in, first-run bootstrap, one additional
  administrator invitation, family-member management, and chore/checklist
  management with a reward-neutral chore weight.
- Homestead, Quest, and Sticker Club v2 themes for family screens, plus themed
  signed-in administrator layouts.
- Docker Compose and Helm deployment assets, liveness/readiness health
  endpoints, and a tested SQLite backup/restore procedure.

### Explicitly out of scope

- Child identities, child sign-in, and per-child authorization. Profile
  selection is a household convenience, not authentication.
- Multi-family tenancy or more than two administrators.
- Horizontal scaling of the backend or multiple SQLite writers.
- Sending weekly report email. Email/SMTP configuration is optional and
  validated, but report email delivery and retry handling are not implemented
  in the MVP; production does not require email settings.
- Persistent game systems such as currencies, reward economies, or
  inventories. Quest derives XP and levels from completion facts and the
  snapshot chore weight at read time; no XP, level, or reward state is stored.
  The weekly-report reward flag is an administrative audit record, not a reward
  system.

### Known limitations

- **Child-facing endpoints are unauthenticated.** Anyone who can reach the app
  can select a profile and tick chores. Run it only on a trusted household
  network, and put it behind TLS and network controls if it is reachable from
  outside the home.
- **SQLite is single-writer.** Run exactly one backend process and one backend
  replica, and use a ReadWriteOnce volume. There is no high availability or
  rolling upgrade for the backend.
- **Weekly reports are generated only by the rollover scheduler.** Assignments
  can be generated manually for a selected week from the administrator UI, but
  reports are still created only by the Monday rollover. Configure the family
  and chore catalog before the first rollover; later catalog changes apply to
  the next generated week.
- **There is no passkey reset flow.** Enroll the second administrator as a
  recovery path. If every passkey is lost, recovery requires a database backup
  or operator intervention.
- Historical assignment, completion, and report rows are immutable by design.
  Do not edit them to "fix" a week; use the retry-safe rollover procedures in
  [Operations](docs/operations.md).

## Architecture at a glance

```text
Browser
  |-- React + Vite (development) or nginx (deployed)
  |-- /api proxy
  v
FastAPI (single Uvicorn process)
  |-- API routes
  |-- application services (business rules)
  |-- SQLite adapters
  v
SQLite file: family/chore catalog, weekly assignments and snapshots,
             daily completions, weekly reports, administrator passkeys
```

- The backend is layered into `api`, `application`, and `adapters`. Architecture
  tests enforce the dependency direction and keep HTTP, business rules, and
  persistence separate.
- The API process owns the durable Monday rollover. A SQLite checkpoint makes
  missed weeks recoverable across restarts.
- Weekly assignments and reports store snapshots, so later catalog edits do not
  rewrite history.
- Themes only change presentation. Theme preferences are persisted, but no
  assignment, completion, report, or authentication behavior depends on them.

See [Architecture](docs/architecture.md) for the data model, invariants, and
rollover sequence.

## Quick start

Requirements: Python 3.15 or newer (below 4.0), Node.js 22 or newer, and npm 10
or newer. Tilt, Docker, Helm, and `kubeconform` are optional and only needed for
those workflows.

```bash
# Backend
python3.15 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
alembic upgrade head
python -m chore_tracker
```

In a second terminal:

```bash
cd frontend
npm ci
npm run dev
```

Open <http://localhost:5173>. The administrator screen is
<http://localhost:5173/admin>; the first visitor can claim the initial
administrator account with an email address and a passkey. No credentials are
stored in the repository, and the application never supplies an administrator
from environment variables.

Use `localhost`, not `127.0.0.1`, in the browser: the default passkey relying
party and allowed origin are configured for `http://localhost:5173`.

Migrations are explicit. The application does not migrate the database during
startup, and readiness stays at HTTP 503 until `alembic upgrade head` has
succeeded.

For the full setup, configuration, Tilt, and test instructions, see
[Development](docs/development.md).

## Quality gates

Run these from the repository root unless a command says otherwise:

```bash
# Backend
ruff format --check .
ruff check .
mypy
pytest

# Frontend
cd frontend
npm run lint
npm run typecheck
npm test
npm run build
```

The same commands run in CI, along with Playwright browser tests, the Compose
smoke test, Helm/Kubernetes manifest validation, documentation link checks, and
the backup/restore verification. See [Development](docs/development.md#quality-gates)
for prerequisites and the full list.
